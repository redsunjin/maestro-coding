## 요약 (Executive Summary)

Maestro는 지금까지 "AI 에이전트가 만든 코드 변경을 사람이 승인해 안전하게 머지하는 도구"였다. 이 보고서의 주장은 하나다:

> **Maestro가 코드 도메인에서 검증해 온 승인·결정·이력의 원형(primitive)은 코드에 국한될 이유가 없다. AI 시대의 모든 "일"은 승인·거부·위임·기록을 필요로 하며, Maestro는 그 보편적 결정 레이어(system of record)로 진화할 수 있다.**

핵심 테제 세 가지:

1. **원형은 이미 검증되었다.** `ApprovalRequest/ApprovalDecision` 프로토콜, per-agent 토큰 신원, Pull-first 전달과 `ack`, 조건부 자동승인(WP-008), 파일 영속 이력 — 이 자산들은 이름만 코드에 묶여 있을 뿐, 구조적으로는 이미 범용 결정 레이어의 부품이다 (§7 매핑 표 참조).
2. **decision과 executor의 분리가 범용화의 열쇠다.** Maestro는 이미 "판단(approve/reject)"과 "실행(git merge)"을 분리했다. `git merge`가 executor의 한 종류일 뿐이라면, 지출 집행·문서 발행·API 호출·데이터 접근 허가도 똑같은 자리에 들어갈 수 있다.
3. **성장은 단계적으로.** 1인 오퍼레이터의 로컬 관제탑(현재)에서 출발해, 팀의 결정 채널, 궁극적으로 조직의 감사 가능한 결정 기록 시스템으로 확장한다. 각 단계는 이전 단계의 검증된 자산 위에만 쌓는다.

## 1. 문제/기회 정의 — 왜 "범용 승인·이력" 레이어가 AI 시대에 필요한가

### 1-1. 결재 문화의 전제가 바뀌었다

지금까지의 결재/승인 시스템(전자결재, ServiceNow, Jira Approval)은 전부 **사람이 사람과** 공유·승인·협업하기 위한 것이었다. 요청자도 사람, 승인자도 사람, 시스템은 서식과 라우팅만 제공했다.

AI 시대에는 이 전제가 무너진다:

- **AI가 일을 대신 처리한다.** 코드 작성, 문서 초안, 데이터 분석, 외부 API 호출, 이메일 발송까지 — 산출물의 생산 주체가 사람에서 에이전트로 이동한다.
- **처리량이 사람의 검토 속도를 초과한다.** 에이전트 함대가 하루에 수십~수백 개의 산출물을 만들면, "모든 것을 사람이 하나하나 결재"하는 모델은 물리적으로 불가능해진다.
- **그럼에도 책임은 여전히 사람에게 있다.** 에이전트가 지출을 집행하고 문서를 발행해도, 법적·조직적 책임 주체는 사람이다. 따라서 "누가·무엇을·언제·왜 승인했는가"의 기록은 오히려 더 중요해진다.

### 1-2. 세 가지 관계에서 승인이 폭증한다

| 관계 | 예시 | 오늘의 도구 |
|---|---|---|
| **사람 → AI** | "이 작업을 해도 되는가?" 착수 허가, 계획 승인, 산출물 승인 | Maestro가 코드 도메인에서 이미 수행 (Work Request Intake, 머지 승인) |
| **AI → 사람** | "임계값을 넘었으니 사람이 결정해 달라" 에스컬레이션 | 채팅창의 확인 프롬프트 — 기록도 정책도 없음 |
| **AI ↔ AI** | 리뷰 에이전트가 구현 에이전트의 산출물을 승인/반려, 오케스트레이터가 서브에이전트 결과를 수용 | 각 프레임워크 내부 로그에 파묻힘 — 감사 불가능 |

세 관계 모두에서 일어나는 일은 동일하다: **어떤 행위자(actor)가 결정 요청을 만들고, 다른 행위자가 판단하고, 판단에 따라 무언가 실행되고, 전 과정이 기록된다.** 그런데 이 동일한 패턴을 담는 공용 레이어가 없다. 각 에이전트 프레임워크가 자기만의 확인 프롬프트와 로그를 갖고, 결정의 근거와 이력은 세션이 끝나면 흩어진다.

### 1-3. 기회

- **비어 있는 자리다.** 에이전트 프레임워크들은 실행에 집중하고, 관찰 도구(agentsview 등)는 사후 분석에 집중한다. "결정의 순간"을 소유하는 제품 — 요청을 받고, 정책을 적용하고, 사람을 개입시키고, 불변 이력을 남기는 — 은 아직 표준이 없다.
- **Maestro는 이 자리에 가장 가까이 있다.** 이미 결정 프로토콜·행위자 신원·위임 정책·영속 이력의 동작하는 구현을 코드 도메인에서 갖고 있다. 필요한 것은 새 시스템이 아니라 **일반화**다.
- **로컬 우선이 신뢰의 출발점이다.** 결정 기록은 민감 데이터다. 로컬에서 시작해 사용자가 자기 이력을 소유하는 모델은, 클라우드 SaaS가 출발점인 경쟁자들과 다른 신뢰 곡선을 만든다.

## 2. 코드 너머로의 일반화 — 승인 대상의 추상화

현재 Maestro의 승인 대상은 사실상 하나다: **"이 브랜치를 머지할 것인가?"** 이를 임의의 **의사결정 대상(decision subject)**으로 추상화한다.

### 2-1. 결정 대상의 스펙트럼

| 결정 유형 | 요청 예시 | 승인 시 executor action | 현재 Maestro와의 거리 |
|---|---|---|---|
| **코드 병합** (현재) | "feature/x 브랜치 머지 승인" | `git merge` | 구현 완료 |
| **작업 착수** (현재) | "이 작업 요청을 진행해도 되는가" | 세션 개시 | Phase A 구현 완료 |
| **계획 승인** | "이 작업 계획대로 실행해도 되는가" | 구현 세션 개시 | Phase B 설계 존재 |
| **지출/구매** | "API 크레딧 $50 추가 구매" | 결제 실행 or 기록만 | executor 신규 |
| **문서 발행/발송** | "이 보고서를 고객에게 발송" | 이메일/게시 실행 or 기록만 | executor 신규 |
| **외부 API 호출** | "프로덕션 DB 마이그레이션 실행" | 스크립트 실행 or 기록만 | executor 신규 |
| **데이터 접근** | "에이전트 X에게 고객 데이터 읽기 허가" | 토큰/권한 발급 | executor 신규 |
| **에이전트 액션 일반** | "이 명령을 실행해도 되는가" (도구 호출 승인) | 호출 통과/차단 | 게이트웨이 신규 |

### 2-2. 일반화의 핵심 통찰: executor는 선택 사항이다

위 표에서 중요한 점은 **executor 열의 "or 기록만"**이다. Maestro는 이미 `executorAction: none | merge`를 구분한다 — 즉 "승인하되 실행은 Maestro 밖에서"라는 모드가 처음부터 존재한다.

이것이 범용화를 급진적으로 쉽게 만든다:

- **기록 전용(record-only) 결정**은 executor가 필요 없다. "지출 승인"의 MVP는 결제 시스템 연동이 아니라, "사람이 승인했고 그 기록이 남는다"는 사실 자체다. 실행은 요청자(에이전트)가 승인 결과를 pull한 뒤 스스로 한다.
- 따라서 **새 결정 유형 추가 비용은 executor 구현이 아니라 스키마 필드 몇 개**다. `subjectType`(무엇에 대한 결정인가)과 도메인별 payload만 있으면 요청·판단·이력·정책은 전부 공용이다.
- executor는 결정 유형이 성숙한 뒤에, 유형별로 하나씩, 선택적으로 붙인다 (git merge가 그랬듯).

### 2-3. 메타포의 확장

오케스트레이션 메타포는 그대로 유효하다. 지휘자는 직접 연주하지 않는다 — 연주자들의 연주를 승인하고, 템포를 정하고(정책), 악보에 기록을 남긴다(이력). 지금까지 연주자는 "코드 치는 에이전트"뿐이었지만, 이제 오케스트라에 지출·문서·데이터의 파트가 추가되는 것이다. **레인은 "승인 레인"에서 "결정 채널(decision channel)"로 일반화된다** — 채널마다 다른 결정 유형이 흐를 수 있다.

## 3. 핵심 엔티티 모델 (일반화)

기존 자산을 일반화한 6개 엔티티. 새로 발명하는 것이 아니라 **이미 있는 것의 이름을 바로잡는 것**에 가깝다.

### Actor — 행위자 (human / agent)

결정에 참여하는 모든 주체. 현재의 Agent Registry(`agentId`, `adapterType`, `capabilities`, `tokenHash`, heartbeat)가 원형이다. 일반화 포인트:

- `actorType: human | agent`를 도입해 운영자(사람)도 1급 행위자가 된다. 현재는 사람이 "대시보드 뒤의 익명 존재"(`decidedBy: operator`)인데, 조직 단계에서는 사람 신원도 토큰/계정으로 구분되어야 한다.
- per-agent 토큰 인증(PR #24)은 그대로 **actor 신원의 토대**다. "누가 요청했고 누가 결정했는가"에 답할 수 있는 근거.

### DecisionRequest — 결정 요청

현재의 `ApprovalRequest`를 일반화한 것. `ApprovalRequest`는 **DecisionRequest의 코드 특화형**이다.

- 추가되는 것: `subjectType`(merge / work-intake / plan / spend / publish / data-access / …), `subject`(유형별 payload — 브랜치명+diff 요약은 merge 유형의 payload일 뿐), `requestedActor` / `decidingActor`.
- 유지되는 것: 상태 모델(`pending_decision` → decided), 소스 구분(`agent | legacy | operator`), 프로젝트/채널 귀속.

### Decision — 결정

현재의 `ApprovalDecision` 그대로. 이미 범용적이다:

- `decision: approve | reject | revise | ask | cancel` — 코드에 국한된 어휘가 아니다.
- `executorAction` — 유형별 실행 동작 (merge는 그중 하나, `none`이 기본).
- `delivery: pull + ack` — 결정이 요청자에게 유실 없이 전달되었음을 기록. AI↔AI 시나리오에서 특히 중요하다 (에이전트가 결정을 받았다는 사실 자체가 감사 대상).
- `decidedBy` — Actor 참조로 승격.

### Policy — 정책

"어떤 결정이 자동으로 처리될 수 있고, 무엇이 사람에게 가야 하는가"의 선언. 현재의 조건부 자동승인(WP-008: explicit 플래그, cooldown, dry-run, 중복 차단)이 원형이다. 일반화 포인트:

- 정책의 주어가 넓어진다: "머지 자동승인" → "`subjectType=spend`이고 금액 ≤ $10이고 요청자가 신뢰 에이전트면 자동승인".
- 정책은 **사람이 사전에 명시적으로 서명한 위임장**이다. 정책 밖의 모든 것은 기본값이 "사람에게 에스컬레이션"이다 (§6).

### AuditLog — 불변 이력

현재의 history(`GET /api/history` + `.maestro-history.json` 영속화)가 원형. 일반화 포인트:

- 기록 범위 확장: 결정뿐 아니라 **정책 적용 사실**("이 결정은 정책 P의 조건 C에 의해 자동승인됨"), 위임 발효/회수, 에스컬레이션, ack까지.
- 성격 규정: **append-only**. 수정·삭제 없는 불변 이력이 system of record의 최소 조건이다. (암호학적 체이닝 등 부인방지 강화는 조직 단계의 선택지 — §6.)

### Delegation — 위임

Policy의 특수하고 중요한 형태: "행위자 A가 자기 결정권의 일부를 행위자 B(사람 또는 AI)에게, 조건 C 하에, 기간 T 동안 위임한다". 현재는 WP-008이 "운영자 → 자동승인 정책"이라는 단일 위임만 표현하는데, 일반화하면:

- 사람 → AI: "테스트 통과한 문서 수정은 리뷰 에이전트가 승인해도 된다"
- AI → AI: "오케스트레이터가 서브에이전트 산출물 수용 권한을 가진다 (단 외부 발송은 제외)"
- 모든 위임은 AuditLog에 기록되고, 즉시 회수 가능해야 한다 (per-agent 토큰 revoke가 이미 이 패턴).

### 관계 요약

```
Actor ──요청──▶ DecisionRequest ──판단──▶ Decision ──선택적──▶ Executor
  ▲                                  ▲                            │
  │                             Policy/Delegation                 │
  └── 신원(token) ──┘           (자동판단 or 에스컬레이션)          │
                                     │                            │
                All ──────────▶ AuditLog (append-only) ◀──────────┘
```

## 4. 유스케이스

### (a) 사람 ↔ AI — 위임하되 임계 초과 시 사람 승인

1인 개발자가 에이전트 함대에 리서치·코드·문서 작업을 맡긴다. Delegation으로 "저위험 결정(테스트 통과 머지, $5 이하 API 지출)은 자동승인"을 서명해 둔다. 에이전트가 $30짜리 크레딧 구매를 요청하면 정책 경계를 초과하므로 Maestro 대시보드(스트림덱처럼 옆에 둔 태블릿)의 결정 채널에 노트가 떨어지고, 사람이 탭 한 번으로 승인/반려한다. 저녁에 AuditLog를 열면 오늘 에이전트들이 무엇을 했고 무엇이 자동승인되었는지 악보처럼 되짚어볼 수 있다.

**현재와의 거리**: 코드 머지 부분은 오늘 이미 동작한다. 부족한 것은 `subjectType` 일반화와 정책의 조건 표현력.

### (b) AI ↔ AI — 에이전트가 다른 에이전트의 산출물을 승인/거부

오케스트레이터 에이전트가 서브에이전트 셋에 작업을 배분한다. 리뷰 에이전트가 각 산출물에 대해 DecisionRequest를 받아 `approve/revise`를 결정한다 — 이 결정 자체가 AuditLog에 남는다. 사람은 실시간으로 개입하지 않지만, "어떤 AI가 어떤 근거로 어떤 AI의 산출물을 통과시켰는지"를 사후에 완전하게 감사할 수 있고, 리뷰 에이전트의 결정 품질이 의심되면 그 위임을 회수한다.

**현재와의 거리**: per-agent 토큰과 다중 에이전트 연결 설계(2026-07-20 스펙)가 토대. 부족한 것은 "에이전트가 decider가 되는" 경로 — 현재 결정은 사람(대시보드)만 만든다.

### (c) 조직 결재 대체 — AI-native 전자결재

팀/조직 단계의 장기 시나리오. 구매 요청·문서 발행·배포 승인 같은 전통 결재 항목이 Maestro의 결정 유형으로 등록된다. 차이는: 요청자가 대부분 에이전트이고(사람이 시킨 일을 에이전트가 수행하다 결재가 필요해짐), 1차 검토도 에이전트가 하며(정책 위반 사전 필터), 사람 결재자는 에이전트가 요약·근거를 첨부한 요청만 본다. 결재선(순차 다단계 승인)은 Delegation 체인으로 표현된다.

**현재와의 거리**: 가장 멀다. 다중 사용자, 사람 신원 체계, RBAC가 전부 필요 — 의도적으로 마지막 단계에 둔다.

## 5. 차별화 / 경쟁

### 5-1. 기존 승인 워크플로 도구와의 비교

| | 전자결재 / ServiceNow / Jira Approval | **Maestro (목표상)** |
|---|---|---|
| 설계 전제 | 사람 → 사람 | 사람↔AI, AI↔AI 포함 3관계 |
| 행위자 신원 | 사람 계정 | **per-actor 토큰 (에이전트 1급 시민)** |
| 승인 처리량 | 사람 손 기준 (일 단위) | 정책 자동판단 + 사람은 예외만 (초 단위) |
| 위임 모델 | 부재중 대결재 수준 | **조건부·기간부·즉시회수 Delegation** |
| 이력 | 문서 중심 보관 | **append-only 결정 원장, ack까지 기록** |
| 배포 모델 | 클라우드 SaaS | **로컬 우선** — 이력을 사용자가 소유 |
| 판단↔실행 | 결합 (승인=집행) | **분리 (decision ≠ executor)** |
| UX | 폼과 목록 | 스트림덱+리듬게임 — 고빈도 결정에 최적화 |

기존 도구들도 AI 기능을 붙이겠지만, "사람 결재선" 모델 위에 AI를 얹는 것과 "행위자 무차별(actor-agnostic) 결정 레이어"를 처음부터 설계하는 것은 다르다. Maestro의 무기는 후자를 **이미 동작하는 코드로** 갖고 있다는 것이다.

### 5-2. 에이전트 생태계 내 포지션: 관찰 vs 통제

- **agentsview 류 (observability)**: 에이전트가 무엇을 했는지 **관찰·분석**한다. 사후적이고 수동적(passive)이다. → 기존 결정대로 이 영역은 재구현하지 않고 위임한다.
- **Maestro (control)**: 에이전트가 무엇을 해도 되는지 **결정의 길목에서 통제**한다. 사전적이고 능동적이다.
- 둘은 경쟁이 아니라 보완이다. 관찰 도구가 "블랙박스 리코더"라면 Maestro는 "관제탑"이다.

### 5-3. 에이전트 프레임워크의 내장 확인 기능과의 관계

Claude Code의 permission 시스템 등 프레임워크 내장 확인 기능은 (1) 해당 프레임워크에 갇혀 있고, (2) 세션과 함께 사라지며, (3) 정책·위임·이력의 체계가 없다. Maestro는 어댑터 계층(hook/wrapper/native)으로 **프레임워크 횡단적인** 결정 레이어를 제공한다 — 어떤 CLI를 쓰든 결정과 이력은 한 곳에 모인다.

## 6. 신뢰 · 거버넌스

system of record를 자처하려면 기능보다 신뢰 속성이 먼저다.

### 6-1. 감사가능성 (Auditability)

모든 결정에 대해 다섯 질문에 답할 수 있어야 한다: **누가**(Actor, 토큰으로 뒷받침) · **무엇을**(subject 스냅샷 — 승인 시점의 대상이 나중에 변조되지 않도록) · **언제**(타임스탬프) · **어떻게**(수동 / 정책 자동 / 위임) · **왜**(comment, 정책이면 어떤 조건이 발화했는지). 현재 history는 누가/무엇/언제를 담고, WP-008 이벤트 로그가 "어떻게/왜"의 원형을 갖고 있다 — 이를 하나의 원장으로 통합한다.

### 6-2. 부인방지 (Non-repudiation) — 단계적으로

- 개인 단계: append-only 파일 원장 + actor 토큰이면 충분하다. 위협 모델이 "자기 기록의 유실"이지 "적대적 변조"가 아니다.
- 팀 단계: 이력 export(서명 포함)와 백업.
- 조직 단계에서만: 해시 체이닝, 외부 타임스탬프 앵커링 등을 검토. **지금 구현하지 않는다** — 다만 이력 레코드 포맷이 나중에 체이닝을 추가할 수 있는 구조(레코드 단위 직렬화)인지만 유지한다.

### 6-3. AI 자동승인 허용 경계 (확정 철학: 정책 내 위임 + 사람 에스컬레이션)

1. **기본값은 사람이다.** 명시적 정책이 없는 모든 결정 유형·조건은 사람에게 간다. 자동승인은 opt-in이며, 이는 WP-008의 `REQUIRE_EXPLICIT` 철학의 계승이다.
2. **정책은 사람이 사전에 서명한 위임장이다.** AI가 스스로 자기 권한을 넓힐 수 없다. 정책의 생성·변경 자체가 사람 승인이 필요한 결정이다 (메타 결정).
3. **경계 초과는 무조건 에스컬레이션.** 한도·범위·기간을 벗어나면 자동 거부가 아니라 사람에게 올린다 — AI는 "모르면 사람에게 묻는" 존재로 설계한다.
4. **모든 자동승인은 회고 가능해야 한다.** dry-run 모드(정책을 켜기 전 "이 정책이 있었다면 무엇이 자동승인되었을까" 시뮬레이션 — WP-008에 이미 존재)를 정책 도입의 표준 절차로 삼는다.
5. **위임은 즉시 회수 가능하다.** revoke 한 번으로 해당 위임 경로가 닫힌다 (토큰 revoke와 동일 패턴).
6. **넘을 수 없는 선(하드 리밋)**: 정책 변경 승인, 위임 생성/확대, 이력 삭제(애초에 불가), 그리고 게임 요소가 결정에 개입하는 것 — 판정 등급·콤보·점수는 어떤 단계에서도 점수 전용이며 실제 결정에 영향을 주지 않는다.

## 7. 아키텍처 진화 경로 — 현재 자산의 일반화 매핑

**이 표가 이 보고서의 중심이다.** 새로 짓는 것이 아니라, 검증된 부품의 이름과 스키마를 넓히는 것임을 보여준다.

| 현재 자산 (검증 상태) | 일반화 후 | 무엇이 바뀌나 |
|---|---|---|
| Agent Registry + per-agent 토큰 (`tokenHash`, `MAESTRO_AGENT_AUTH_ENFORCE`, PR #24) | **Actor** (human/agent 공용 신원) | `actorType` 추가, 사람 신원은 팀 단계에서 |
| `ApprovalRequest` (store + 영속화) | **DecisionRequest** | `subjectType` + 유형별 `subject` payload 추가. ApprovalRequest는 `subjectType=merge` 특화형으로 재해석 |
| `ApprovalDecision` (5어휘 + delivery/ack) | **Decision** | 거의 그대로 — 어휘가 이미 범용적 |
| Pull-first 전달 + `ack` | 결정 전달 계약 그대로 | 변화 없음. AI↔AI에서 "수신 사실의 감사"로 가치 상승 |
| executor 분리 (`executorAction: none\|merge`) | **Executor 플러그인 지점** | `merge` 외 유형별 executor를 선택적으로 추가. `none`(기록 전용)이 신규 유형의 기본값 |
| 조건부 자동승인 WP-008 (explicit/cooldown/dry-run) | **Policy / Delegation** | 조건의 주어를 `subjectType`·금액·요청자 신뢰도 등으로 확장, 위임의 1급 엔티티화 |
| History (`GET /api/history` + `.maestro-history.json`) | **AuditLog** (append-only 원장) | 기록 범위 확장 (정책 발화, 위임, 에스컬레이션). 포맷은 체이닝 추가 가능하게 유지 |
| 레인 (1~8, 프로젝트별) | **결정 채널 (decision channel)** | 채널=결정 유형/출처별 스트림. UI 개념은 그대로 |
| Work Request Intake (Phase A) | `subjectType=work-intake`인 DecisionRequest | 별도 시스템이 아니라 첫 번째 비-머지 결정 유형이었음이 드러남 |
| Work Console 세션 | 결정 전후의 **대화 맥락 기록** | AuditLog의 "왜"를 보강하는 부속 기록 |
| 어댑터 계층 (hook/wrapper/native/예약 discovery) | 요청 **ingress 일반화** | 코드 외 도메인의 요청도 같은 어댑터 문법으로 유입 |

### 진화의 순서 원칙

1. **스키마 먼저, executor 나중.** `subjectType`과 record-only 결정을 먼저 열면, 코드 한 줄 실행하지 않고도 새 도메인의 승인·이력이 동작한다.
2. **기존 경로 무회귀.** `/api/request`(legacy)와 머지 승인 UX는 그대로 두고, 일반화는 새 필드·새 유형의 추가로만 진행한다 (VU-001이 지켜온 가드레일 그대로: 기능 플래그, 네임스페이스 격리).
3. **VU-001과 합류.** Phase B(계획 승인)·Phase C(Delivery Bridge)는 이 비전의 부분집합이다 — "계획"과 "산출물 승격"도 결정 유형이다. 별도 트랙이 아니라 같은 방향의 걸음으로 재해석한다.

## 8. 단계적 로드맵 + 리스크 / YAGNI 경계

### Stage 1 — 개인: "1인 오퍼레이터의 만능 관제탑" (다음 반년의 방향)

- `subjectType` 도입 + record-only(비-머지) 결정 유형 1~2개를 실전 투입 (후보: 지출 승인, 외부 발송 승인 — 실제로 내 에이전트 운영에서 빈번한 것부터)
- 에이전트가 decider가 되는 최소 경로 (AI↔AI 유스케이스 (b)의 수직 슬라이스)
- Policy 조건 표현 확장 (subjectType·한도 기반) + 에스컬레이션 동작
- AuditLog 통합 (history + WP-008 이벤트 + 위임 기록을 한 원장 뷰로)
- 진행 중인 VU-001 Phase B/C를 이 어휘로 완성

**Stage 1 성공 기준**: 코드가 아닌 결정 유형 하나가, 어댑터→요청→정책 판단→(자동승인 또는 사람 탭)→ack→이력까지 기존 머지 승인과 동일한 신뢰도로 흐른다.

### Stage 2 — 팀: "결정 채널의 공유"

- 사람 Actor 신원 (운영자 복수화), 결정 채널 구독/알림
- 이력 export + 서명, 팀 단위 정책 공유
- 원격 에이전트 연결 (다중 에이전트 설계의 시나리오 B)

### Stage 3 — 조직: "AI-native system of record"

- 결재선(Delegation 체인), RBAC, 부인방지 강화(해시 체이닝 등)
- 규정 준수 리포팅

### 리스크 (내부 문서로서 솔직하게)

| 리스크 | 내용 | 완화 |
|---|---|---|
| **범용화의 저주** | "모든 것의 승인 도구"는 "아무것도 아닌 도구"가 되기 쉽다. 추상화가 실사용을 앞지르면 죽은 스키마만 남는다 | 결정 유형은 **내가 실제로 매주 겪는 승인**부터 하나씩. 유형 추가는 실사용 증거 필요 |
| 단일 사용자 가정의 깊이 | 현 코드베이스는 1인 운영 가정이 UI·인증·저장 전반에 배어 있어 팀 단계 비용이 클 수 있다 | Stage 1에서는 건드리지 않되, 새로 쓰는 스키마에만 actor 참조를 명시해 부채를 늘리지 않는다 |
| 신뢰 주장 대비 구현 격차 | "system of record"를 표방하며 파일 기반 저장이 유실되면 신뢰가 역효과 | 단계에 맞는 주장만 한다: 개인 단계에서는 "내 결정의 기록", 부인방지는 조직 단계에서만 표방 |
| 게임 UX와 진지한 도메인의 충돌 | 지출·데이터 접근 승인에 리듬게임 톤이 가벼워 보일 수 있다 | 게임 요소는 지금처럼 점수 전용 + 채널별 톤 조절 가능성만 열어둔다 (지금 구현 안 함) |
| 경쟁 진입 | 에이전트 프레임워크 자체가 승인 레이어를 내장 확장할 수 있다 | 프레임워크 횡단성(어댑터)과 이력 소유(로컬 우선)가 방어선 — 단일 프레임워크 내장 기능이 줄 수 없는 것 |

### YAGNI 경계 — 이 비전이 **말하지 않는 것** (지금 하지 않는다)

- 결제/이메일/권한 시스템과의 실제 executor 연동 (record-only로 충분할 때까지)
- 해시 체이닝·블록체인·외부 앵커링 (조직 단계 전까지)
- RBAC / 다중 운영자 동시 편집 (팀 단계 전까지)
- 워크플로 빌더 / 폼 디자이너 (전자결재 흉내는 함정 — Maestro의 가치는 서식이 아니라 결정 원장)
- 관찰/분석 기능 재구현 (agentsview 위임 결정 유지)
- 클라우드 SaaS 전환 (로컬 우선은 정체성)
- 기존 `/api/request`·머지 승인 UX의 파괴적 변경

## 9. 네이밍 · 포지셔닝 (확정: 메타포 유지·확장)

- **Maestro 브랜드와 오케스트레이션 메타포를 유지한다.** "지휘자는 직접 연주하지 않고, 연주자들을 승인·조율하며, 모든 연주는 악보(이력)에 남는다"는 서사는 코드 전용일 때보다 범용 결정 레이어일 때 오히려 더 정확해진다.
- 어휘의 일반화: **레인 → 결정 채널**(decision channel), **승인 노트 → 결정 노트**, **악보뷰 → 결정 원장 뷰**. 기존 사용자에게는 연속적이고, 새 도메인에는 자연스럽다.
- 포지셔닝 한 줄 (내부 기준): **"Maestro — AI 시대의 결정 관제탑. 사람과 AI, AI와 AI 사이의 모든 승인·거부·위임을 하나의 감사 가능한 원장으로."**
- 태그라인 후보 (외부용, 참고): "Conduct your agents." / "코딩을 지휘하다"에서 "일을 지휘하다"로.
