# Work Console Risk Review

기준일: 2026-03-28
대상 트랙: `VU-001`
상태: 설계 초안

## 1. 왜 리스크 검토가 중요한가

Work Console은 단순 UI 추가가 아니다.

- 작업 지시
- 대화
- 계획 승인
- 커밋 제안
- 전달물 승격

을 한 화면 안에 담기 때문에, 잘못 설계하면 Maestro의 핵심인 승인 안정성을 해칠 수 있다.

## 2. 최고 우선 리스크

### R1. 채팅이 승인 시스템을 우회하는 리스크

설명:

- 사용자가 채팅창에서 `/merge` 같은 행동을 기대하기 시작하면 기존 승인 레인이 무력화된다.

영향:

- 승인 추적성 붕괴
- 잘못된 merge 가능성 증가

대응:

- `/merge`, 직접 `undo/reset` 명령 금지
- 최종 merge는 기존 레인에서만 수행

### R2. 자유 채팅이 상태 추적을 흐리는 리스크

설명:

- 중요한 결정을 텍스트 대화로만 남기면 나중에 복기와 감사가 어렵다.

대응:

- plan, commit proposal, delivery는 반드시 카드화
- decision 버튼 또는 명령 결과로만 상태 전이 허용

### R3. 패널 복잡도가 기존 운영 UX를 해치는 리스크

설명:

- Work Console이 너무 무거우면 현재 `History/Repo/AutoOps`보다 우선순위를 침범한다.

대응:

- 기본 닫힘
- 도킹형 패널
- 좁은 화면에서는 축소 모드
- MVP에서 기능 과적재 금지

### R4. OpenClaw 연결 실패가 전체 운영을 막는 리스크

설명:

- 외부 비서 연결이 불안정할 경우 운영자가 패널을 신뢰하지 않게 된다.

대응:

- 세션 상태에 `waiting`, `failed`, `needs_reconnect` 명시
- 기존 승인 기능은 완전 독립 유지

### R5. 명령 남용 리스크

설명:

- `/commit`, `/deliver`, `/close`를 상태와 무관하게 남발하면 잘못된 상태 전이가 발생할 수 있다.

대응:

- 상태 기반 명령 허용 목록
- 잘못된 상태에서 명령 실행 시 `COMMAND_REJECTED`

## 3. 중간 우선 리스크

### R6. 장기 세션 메모리/성능 리스크

- 메시지와 카드가 누적되면 렌더/저장 비용이 커진다.
- 대응: 최근 N개 렌더, 나머지 페이지네이션

### R7. 다중 운영자 충돌 리스크

- 같은 카드에 여러 사용자가 다른 판단을 내릴 수 있다.
- 대응: MVP는 단일 운영자 기준 고정, 다중 운영자는 후속 단계

### R8. 커밋 제안 오해 리스크

- 사용자가 `/commit`을 즉시 git commit으로 오해할 수 있다.
- 대응: UI 라벨을 `Commit Proposal`로 고정, 결과 카드에 proposal-only 명시

### R9. 세션-프로젝트 매핑 혼선

- 프로젝트 전환 후 잘못된 세션에서 명령을 보낼 수 있다.
- 대응: 세션 헤더에 프로젝트 이름/레인 표시, 활성 프로젝트와 다르면 경고

## 4. UX 검토 포인트

### 유지해야 할 것

- 현재 레인 승인 UX의 즉시성
- `History`와 `Repo` 패널의 단순성

### 추가해야 할 것

- 세션 리스트와 현재 세션의 분리
- 카드 타입별 시각적 구분
- operator action이 필요한 상태 강조

### 피해야 할 것

- 메신저 앱처럼 모든 이벤트를 동일 버블로 렌더
- 화려한 실시간 애니메이션 남용
- 승인 관련 핵심 경고를 채팅 로그 속에 묻기

## 5. 기술 검토 포인트

### 저장

- Work Console 데이터는 기존 history와 별도 store 필요
- 메시지, 카드, 결정 로그를 분리 저장해야 함

### 이벤트

- `WORK_*`, `COMMAND_*`, `COMMIT_PROPOSAL_*` 네임스페이스 분리 필요

### 프런트 구조

- 기존 App에 직접 다 넣지 말고 별도 훅/패널/타임라인 렌더러로 분리해야 함

## 6. 도입 가드레일

1. 기능 플래그 뒤에서 시작
2. Phase 단위 도입
3. 기존 레인 승인과 분리
4. proposal-only 정책 유지
5. 파일럿 운영자 1명 기준으로 검증

## 7. Go / No-Go 기준

### Go

- 채팅이 아닌 작업 관제 패널로 정의가 유지됨
- 최종 merge 우회 경로가 없음
- 세션/카드/결정이 복기 가능함

### No-Go

- 자유 채팅 요구 때문에 상태 추적이 희생됨
- merge/rollback을 콘솔에서 직접 처리하려 함
- UI 복잡도가 레인 승인 UX를 해침

## 8. 권장 다음 단계

1. `Work Console Shell UI`만 먼저 구현
2. 세션/메시지 저장 추가
3. 명령 프로토콜 최소 세트 적용
4. `Plan Card`와 `Commit Proposal Card` 도입
5. 마지막에 `Delivery -> Approval Lane` 브리지 연결
